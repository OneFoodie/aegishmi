## 1. 目的与范围

把对标 Chroma 8000 / 固纬 ATS / 研华 TestExec / Keysight Test Exec SL 后剩下的差距，
整理成可执行、可验收的开发计划。范围限定在**单机工位上位机**能力内：

- 纳入：固件/版本校验、设备多链路、链路心跳、流程控制（条件/跳转/循环）、工步瓶颈、
  MES 上传响应与过站校验、多语言、自动更新（轻量版本检测）、GPIB/USBTMC 仪器、
  独立质检角色、工位侧扫码 + BOM 查询钩子、用户代码模块（插件）。
- 不纳入：多工位并行/汇总、物料主数据维护/BOM 下发、维修记录、LDAP 等依赖上层系统或
  需要架构重写的条目，统一列在第 8 节"明确不做/外部依赖"。

## 4. 详细方案

### 4.1 TP-08 固件/版本校验（P1）

**目标**：测试流程中能"读设备版本 → 与 BOM/工单要求比对 → 判定 PASS/FAIL 并留痕"，
替代当前只能靠人工确认版本的方式。

**设计要点**

1. 流程模型新增 `StepAction::ReadVersion`（或复用 `command` + 新命令字，二选一，推荐新增 action 更直观）：
   - `params`: `cmd`（如 `READ_VERSION` / SCPI 查询）、`channel` 可选；
   - `expect`: 新增字符串字段 `version`（精确匹配）与 `versionPattern`（正则，二选一）；
     `ExpectSpec` 目前只有数值字段，需要扩 `QString expectedVersion / versionPattern`。
2. 设备抽象扩展：`ITestDevice` 增加字符串回传能力，例如
   `virtual bool queryText(const QString& cmd, QString* value, QString* error)`；
   现有 `sendCommand` 只有 `quint8 status`，无法带回版本号。
3. 各协议实现：
   - SCPI：复用 `ScpiClient::query()`，默认命令 `*IDN?`（可配置 `SYST:VERS?`）；
   - 自定义 TCP：新增 `CommandId::ReadVersion` + 帧编解码（`frame.h` / `frame_codec`），
     设备端返回 ASCII 版本串或版本码；
   - Modbus：保持寄存器 `0x0100` 起 12 个（24 字节 ASCII，大端，NUL 之后忽略）；
   - OPC UA：读取版本文本节点 `ns=1;s=FirmwareVersion`（String）。
4. 校验与执行：
   - `flow_validator`：版本步骤必须配置 `version` 或 `versionPattern` 之一，禁止 min/max；
   - `test_engine`：查询结果按精确/正则比对，写入步骤实测值（文本）；
   - 失败策略沿用 `retries` / `onFail`。
5. 存储与展示：
   - `storage::HistoryStep` 目前只有 `double measured + QString unit`，版本号写入 `message`，
     在 `pdf_report` 步骤表"说明"列展示；如需按版本号检索再新增结构化列。
6. 编辑器：`flow_editor_dialog` 动作下拉增加"读版本"，属性面板增加"期望版本/正则"输入框。

**涉及文件（预估）**

- `src/test/flow_types.h`、`flow_loader.cpp`、`flow_validator.cpp`、`flow_writer.cpp`
- `src/test/test_engine.cpp`、`test_device.h`、`device_command.h`
- `src/service/device_service.{h,cpp}`（SCPI 查询 / 自定义帧 / Modbus / OPC UA）
- `src/protocol/frame.h`、`frame_codec.*`、模拟器 `simulator/main.cpp`
- `src/ui/flow_editor_dialog.cpp`
- `tests/tst_flow.cpp`、`tst_engine.cpp`

**验收标准**

- 流程中加入"读版本"步骤后，模拟器返回版本与期望一致 → PASS，不一致 → FAIL（含实际版本）。
- 正则匹配（如 `^v\\d+\\.\\d+`）可用；版本为空/查询超时按失败处理并给出原因。
- 编辑器可创建/编辑/保存该步骤，保存后 JSON 往返一致（`tst_flow` roundtrip）。
- PDF 报告的步骤明细能看到实际版本号。

**实施记录（2026-11-26，已完成）**

- 流程模型：`StepAction::ReadVersion`；`ExpectSpec` 新增 `version` / `versionPattern`；
  `flow_loader` 解析 `readVersion`，`flow_validator` 校验"二选一、正则合法、禁止数值条件"，
  `flow_writer` 写回 `params.cmd` 与 `expect.version/versionPattern`。
- 设备抽象：`ITestDevice::queryText(cmd, timeoutMs, value, error)`；`DeviceService` 实现
  SCPI 查询（默认 `*IDN?`）与自定义协议 `CommandId::ReadVersion`（Info 帧回同序号文本）。
- Modbus/OPC UA：`ModbusTcpClient` / `ModbusRtuClient` 新增 FC03 读保持寄存器，
  `DeviceService` 读 `0x0100` 起 12 个寄存器并按大端 ASCII 解码（NUL 截断）；
  `OpcUaClient` 新增 `readString`，读 `ns=1;s=FirmwareVersion`（`params.cmd` 以 `ns=` 开头可指定其他节点）。
- 执行与展示：`TestEngine` 精确/正则比对，实际版本写入步骤说明；编辑器动作下拉新增
  "读取版本"及"期望版本/版本正则"输入；模拟器（自定义帧/SCPI/Modbus/OPC UA）均返回同一版本串。
- 测试：`tst_flow`（加载/校验/往返）、`tst_engine`（通过/不匹配/正则/设备错误）、
  `tst_deviceservice`（ReadVersion → Info 帧、Modbus FC03 版本寄存器）、
  `tst_opcua`（FirmwareVersion 节点读取 + `queryText` 链路）、`tst_modbus`（FC03 编码）。
  `ctest` 11/11 通过。

### 4.2 EQ-06 串口/网口多链路（P1）

**目标**：一台设备可同时挂两条链路（例如"自定义 TCP 采集波形 + SCPI 仪器读电压"），
两条链路并行工作、互不串扰。

**现状约束**：`DeviceSpec` 只有一个 `protocol`，每设备一个 `DeviceService`、一个线程、
一套 `ring_/stats_/connected_/ack/capture/summary` 状态；`connectDevice` 按单协议分支。

**推荐方案：每链路一个 DeviceService（侵入较小）**

1. 配置 schema：`fleet.json` 增加 `links: [ { "id": "main", "protocol": "...", ... } ]`；
   无 `links` 时按现有单链路解析，保持向后兼容。
2. `DeviceSpec` 增加 `QVector<LinkSpec> links`（首条兼容旧字段）；
   `DeviceManager::Entry` 从 `service` 变为 `QMap<QString, DeviceService*> links`。
3. `DeviceManager` 按链路建立多个 `DeviceService`，信号附加 `linkId`；
   采样聚合到设备级：主链路负责波形/摘要，辅助链路只做命令与单点测量（可配置 `role: "main" / "aux"`）。
4. UI：设备列表保持"一台设备一行"，连接参数区增加"链路"下拉；状态显示"主链路已连接 / 辅助链路已连接"。
5. 测试引擎：`ITestDevice::sendCommand` 增加可选 `linkId` 参数，默认主链路。

**方案 B（不推荐）**：把 transport/mode/ack 抽成 `TransportLink` + `DeviceAggregator` 重构。
只有需要"同一通道双源合并"时才值得做，改动面覆盖采样、报警、趋势、测试引擎。

**验收标准**

- 同一设备配置两条链路时可分别连接/断开，任一链路断开不影响另一条。
- 主链路波形/摘要/报警行为与当前单链路完全一致。
- 测试步骤可指定链路下发命令；未指定时走主链路。
- `fleet.json` 旧格式（单 `protocol`）保持可用，日志与 UI 无回归。

**实施记录（2026-11-26，已完成）**

- 配置：`DeviceSpec` 增加 `QVector<LinkSpec> links`（`id/role/protocol/host/port/...`）；
  `fleet.json` 无 `links` 时按原有单链路字段合成一条主链路，旧配置无需改动。
- 服务层：`DeviceManager` 每链路一个 `DeviceService`，新增 `linkIds/mainLinkId/link/linkSpec/
  connectLink/disconnectLink`，信号携带 `deviceId + linkId`；主链路负责波形/摘要/报警。
- 执行层：`ITestDevice::sendCommand/queryText` 增加 `linkId`（空 = 主链路）；
  流程步骤支持 `link` 顶层字段或 `params.link`，`FlowWriter` 写回顶层 `link`；
  编辑器的步骤属性面板新增"链路"输入框（留空 = 主链路）。
- 界面：设备列表仍"一台设备一行"，连接参数区新增"链路"下拉与多链路状态提示。
- 测试：`tst_deviceservice`（双链路独立连接/断开、命令按 linkId 路由、
  `fleet.json` 新旧格式解析）、`tst_engine`（步骤 link 路由）、`tst_flow`（link 解析与保存往返）。
  `ctest` 14/14 通过。

**收尾增强（2026-11-26，已完成）**

- 链路级采样：`ITestDevice::sampleWindow/sampleRateHz` 增加 `linkId`，`LinkRouter` 按链路
  选择设备服务；`measure` 步骤与脚本里的 `measureAvg` 都用步骤 `link` 对应的链路采集，
  数据不足判定也按该链路采样率计算（主链路断开后仍可从辅助链路取数）。
- 辅助链路单点测量：`ITestDevice::measureOnce`（默认实现 = 一个采样周期窗口取均值），
  脚本新增 `measureOnce(channel)`；同一脚本步骤内的命令/测量统一走该步骤的链路。
- 链路健康面板：`DeviceService` 暴露 `lastInboundAgeMs/reconnectAttempts`，
  `DeviceManager::linkHealth()` 聚合在线状态、最近入站延迟、帧/CRC/字节与重连次数；
  监控页左侧新增"链路健康"表格，每秒刷新（在线绿色 / 离线红色）。
- 10 台模拟仪表连接测试：`configs/devices/fleet_10sim.json`（sim01~sim10，自定义协议端口
  29527~29536）、`tools/linkcheck.cpp`（`aegis_linkcheck` 无界面连接全部链路并检查入站帧）、
  `scripts/sim10_connect_test.ps1`（一键启动/验收/清理）。实测 10/10 在线且有数据。
- 测试：`tst_engine`（measure 步骤与脚本单点测量按 link 路由、按链路采样率判定）、
  `tst_deviceservice`（健康快照字段、主链路断开后辅助链路采样与单点测量可用）。
  `ctest` 14/14 通过。

### 4.3 SY-06 多语言（P3）

**目标**：界面支持中/英切换，切换后立即生效（无需重启），PDF 报告标题/表头跟随语言。

**设计要点**

1. 基础设施：CMake 引入 `Qt6::LinguistTools`，启用 `qt_add_translations`；建立 `translations/aegis_zh_CN.ts`、`aegis_en_US.ts`。
2. 字符串改造：把所有面向用户的中文 `QStringLiteral` 改为 `tr("...")`，覆盖 `src/ui/*`、
   `flow_validator.cpp`、`device_service.cpp` 日志、`pdf_report.cpp` 表头/签名栏。
3. 语言管理：新增 `core::LanguageManager`（或 `MainWindow` 内实现）：
   - 启动时读取 `QSettings("ui/language")`，默认跟随系统；
   - `QTranslator` 加载 `.qm`；切换后重建页签或发送 `languageChanged` 信号刷新文案；
   - 菜单/按钮入口："设置 → 语言：中文 / English"。
4. 数据与格式：日期时间用 `QLocale` 格式化；`station.json` 的报告标题/页脚可按语言提供
   `title` / `titleEn` 之类的可选字段（缺省回退中文）。
5. PDF 字体：英文环境优先 `Microsoft YaHei`，缺失时回退 `Arial`，避免方框。

**验收标准**

- 中文/英文切换后，主窗口、监控页、测试页、历史页、报警页文案全部更新，无残留中文（品牌名除外）。
- 切换语言不影响正在运行的测试；重启后保持上次语言。
- PDF 报告在英文环境下无乱码，日期/数字格式符合 `en_US`。
- 新增 `tst_i18n`（或并入 `tst_core`）：验证翻译文件可加载、关键文案能翻译。

### 4.4 SY-05 自动更新（P3，轻量版本检测）

**目标**：启动或手动检查版本清单，发现新版本时提示升级包位置与校验值；
不在程序内静默下载安装，降低现场风险。

**设计要点**

1. 版本来源：`version.json`（含 `version / notes / url / sha256 / minVersion`），
   放在内网 HTTP、共享目录或随升级包分发；地址写入 `station.json` 的 `update` 段。
2. 检查策略：启动后延迟检查一次 + "关于/检查更新"手动入口；只读清单，结果写日志。
3. 校验：若清单提供 `url`，按需下载升级包到临时目录并校验 SHA-256；
   不匹配则拒绝并提示，不在程序内直接覆盖运行中的文件。
4. 安装：提示"请退出程序后运行升级包"；升级脚本保留 `configs/` 与用户数据目录，
   升级后启动回读版本号确认。
5. 安全：只允许 HTTPS 或内网清单地址，禁止任意 URL；无清单/离线时静默跳过。

**验收标准**

- 内网目录中的 `version.json` 可被检测，版本比较正确并提示。
- SHA-256 不匹配时拒绝并留日志。
- 检查更新不需要管理员权限；升级后 `configs/` 与数据库不丢失，界面显示新版本号。
- 无更新源/离线时静默跳过，不影响正常开机。

### 4.5 EQ-05 余项：GPIB/USBTMC（P2，硬件依赖）

**目标**：在 SCPI-RAW TCP 之外，支持 GPIB 与 USBTMC 仪器。

**设计要点**

- 抽象 `IScpiTransport`（`write/read/超时/打开关闭`），现有 TCP 实现迁入；
  GPIB 通过厂商 VISA/驱动（如 NI-VISA、Keysight IO Libraries）提供 DLL 适配层；
  USBTMC 走 WinUSB/libusb 或厂商 SDK。
- 保持 `ScpiClient` 上层协议逻辑（在途请求排队、轮询事务号 0）不变，只替换 transport。
- 配置：`protocol: "scpi"` 增加 `transport: "tcp" | "visa" | "usbtmc"`，地址字段按类型使用 `host:port` 或 `visaResource`。
- 无硬件时以 mock transport 做单测；驱动缺失时在 UI 明确提示。

**验收标准**

- 无第三方驱动时编译/运行不受影响，仅对应链路不可用。
- 有 VISA 环境时可通过资源串（如 `GPIB0::22::INSTR`）完成 `*IDN?` 与周期测量。
- 现有 TCP SCPI 用例全部保持通过。

### 4.6 QA-07+ 独立质检角色（P3）

**目标**：把双人复核从"任意操作员/管理员"升级为"质检角色"授权，贴合客户审计要求。

**设计要点**

- `Role` 增加 `Quality`（或在 `Permission` 增加 `Approve`），默认账号可配置；
- 复核校验改为要求 `Approve` 权限；工位配置可开关"复核人必须为质检角色"；
- 用户管理页支持设置质检角色；审计继续记录复核人。

**验收标准**

- 质检角色可复核、普通操作员不可复核（可配置回退到旧行为）。
- 登录/权限/4-eyes 现有测试按新角色更新并通过。

### 4.7 TP-11 用户代码模块/插件（P3）

**目标**：测试序列可调用用户提供的 C#/Python/LabVIEW 代码做定制判定或数据处理，
不改动主程序，补齐商用工具常见的"用户代码模块"能力。

**推荐方案：独立进程 + JSON stdio**

1. 插件形态：每个插件一个目录 `plugins/<name>/`，含 `manifest.json`
   （名称、版本、入口命令、参数 schema、默认超时）与可执行入口。
2. 调用协议：主程序以子进程启动入口，stdin 写一行 JSON（步骤参数 + 上下文
   SN/工单/方案 + 前序测量值），stdout 读一行 JSON（`pass/fail` + `message`
   + 可选 `measures`）；stderr 收日志。
3. 流程集成：新增 `StepAction::Plugin`（或在 `command` 中增加 `plugin` 字段）；
   `flow_loader` 解析、`flow_validator` 校验插件存在且参数符合 manifest。
4. 隔离与安全：`station.json` 的 `plugins.enabled` 白名单；单次调用超时（默认 5s）；
   非零退出、超时、输出非 JSON 均按步骤失败处理，不影响后续步骤与主进程。
5. 示例：`plugins/example_python/` 提供 Python 示例（读 JSON、判定电压范围、返回结果），
   用于验收与现场参考。

**涉及文件（预估）**

- `src/test/flow_types.h`、`flow_loader.cpp`、`flow_validator.cpp`、`flow_writer.cpp`
- `src/test/plugin_runner.{h,cpp}`（新增，QProcess + JSON 编解码）
- `src/test/test_engine.cpp`
- `tests/tst_plugin.cpp`（新增）

**验收标准**

- Python 示例插件可被流程调用并返回 PASS/FAIL，实测值写入步骤说明。
- 插件超时、崩溃、输出非 JSON 时步骤失败，后续步骤仍可继续。
- 未在白名单内的插件在方案校验期报错，无法启动测试。

### 4.8 PL-08 工位侧物料防错（P3）

**目标**：在不接管 MES 物料主数据的前提下，工位侧用扫码枪校验"当前上料与工单 BOM 是否一致"，
不一致时锁站，避免错料流入。

**边界**：BOM 维护、料盘台账、发料/退料仍在 MES；本功能只做"扫码 + 只读查询 + 本地拦截"。

**设计要点**

1. 输入：扫码枪按键盘设备接入（焦点输入框 + 回车触发），支持手工输入；
   扫码值写入运行上下文。
2. 查询：`station.json` 的 `mes` 段增加 `bomCheckPath`（如 `POST /api/bom/check`，
   请求 `{workOrder, product, materialCode}`，返回 `{match, expected}`）；
   复用 `MesUploader` 的 HTTP 客户端与超时配置。
3. 判定：`match=true` 放行并记审计；`match=false` 提示"料号不符"并锁定测试启动，
   需班组长确认后解锁（写审计）。
4. MES 不可用：按 `mesFailOpen` 配置处理——默认"提示后放行"（避免停线），
   严格模式"锁定"。
5. 留痕：扫码值、BOM 期望值、查询结果、操作人写入审计与运行记录；
   PDF 报告可选展示。

**涉及文件（预估）**

- `src/core/station_config.{h,cpp}`（BOM 查询地址、失败策略）
- `src/service/mes_uploader.{h,cpp}` 或新增 `mes_client`（只读查询）
- `src/ui/test_page.{h,cpp}`（扫码输入、锁站提示）
- `tests/tst_mes.cpp`（扩展）

**验收标准**

- 正确料号扫码后放行，错误料号锁站且无法启动测试。
- MES 超时/断网时按 `mesFailOpen` 行为执行，并写审计。
- 扫码值在历史/报告中可追溯。
- 不改变现有 MES 结果上传逻辑。
