## 3. 关键用例设计说明

### 3.1 粘包 / 分包（tst_core）

- 把两帧拼成一个字节块一次性喂入 → 期望回调 2 次；
- 一帧分 3 段喂入（含 1 字节、6 字节、剩余）→ 期望只回调 1 次且内容完整；
- 帧前插入 `0x00 0xAA 0xAA 0x55` 垃圾 → 期望能对齐到正确帧头；
- 篡改 CRC → 期望 `crcErrors == 1` 且不产生回调，随后紧跟的好帧仍能解析。

### 3.2 命令应答（tst_deviceservice）

进程内启动假设备（QTcpServer）与假 Modbus 服务端：

- 假设备对 SET_VOUT 校验范围（0~15000 mV），越界回 status=1；
- 上位机 `sendCommand` 在超时内返回 true 且 status 正确；
- 不回复的假设备 → `sendCommand` 在超时后返回 false；
- Modbus：FC06 写寄存器 0 后，假服务端后续 FC04 回读值随之改变（验证写生效）。

### 3.3 采样率自适应（tst_engine + tst_deviceservice）

`ITestDevice::sampleRateHz()` 让引擎按协议计算期望点数；
Mock 设备声明 20 Hz、窗口 200 ms → 期望 4 点，不会因"不足 10 kHz 比例"误判失败。

### 3.4 OPC UA（tst_opcua）

- 测试内启动 `UA_Server`（独立线程迭代事件循环），暴露 `ns=1;s=Channel0/1`（节点 0 可写）；
- **订阅读**：`OpcUaClient` 连接 → 等待 `valuesUpdated` → 断言数值 1234 / 5678；
- **写节点**：写入节点 0 = 4321 → 断言 `writeCompleted(ok)`；用第二个客户端订阅该节点，
  从服务端重新读到 4321，证明写入真正落到设备侧；
- **DeviceService 链路**：`connectOpcUa` → 在独立线程 `sendCommand(SET_VOUT, 7000)` →
  主线程处理队列信号唤醒等待 → 独立客户端回读 7000（验证命令映射与事务号匹配）；
- **错误端点**：连接未监听端口 → 断言收到 `failed` 且不崩溃。

## 4. 性能测试

### 4.1 基准程序

```bat
build-mingw\bin\aegis_bench.exe
```

**实测输出（Release，单次运行；多次运行波动约 ±10%）：**

| 项目 | 数值 |
|---|---|
| 单帧字节数 | 1213 B（100 点 × 6 通道 + 头/CRC） |
| 单帧解码耗时 | 0.010 ms |
| 采样点吞吐 | 58.41 M 点/秒 |
| 单核可支撑 | ≈ 9734 kHz × 6 通道 |
| 环形缓冲 push+pop | 1.3 ns/次 |
| 环形缓冲吞吐 | 787.8 M 块/秒 |

结论：协议解码不是瓶颈，10 kHz × 6 通道（6 万点/秒）只占用约 0.1% 的单核解码能力。
真正需要优化的是**绘制**，见 4.2。

### 4.2 界面绘制优化对比

| 阶段 | 实现 | 单帧耗时 | 现象 |
|---|---|---|---|
| 优化前 | `QLineSeries::append` 逐点 + QChart 全量重绘 | ≈ 800 ms | 连接后界面卡死 |
| 中间尝试 | 自绘 + `QPen::setWidthF(1.4)` | ≈ 800 ms | 依然卡（gdb 停在 `QRasterPaintEngine::drawPolygon`） |
| 最终方案 | 自绘 + 抽稀 300 Hz + `setWidth(1)` + `setCosmetic(true)` | ≈ 2.7 ms | 20 fps 稳定，CPU ≈ 1% |

关键结论：**非整数宽度画笔会触发 QStroker 矢量描边**，成本与点数强相关；
cosmetic 画笔走快速路径，是实时波形绘制的必要条件。

### 4.3 运行时观测

| 指标 | 观测方式 | 结果 |

| 丢块 | 统计面板 `dropped` | 正常负载下为 0 |
